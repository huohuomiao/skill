# p4 · 缓存与断点续跑

p4 从 p3 独立演进，实现阶段 4 的阶段指纹、内容寻址缓存、断点续跑和变更影响路由。p3 的三种模式、静态策略路由与固定预算保持不变；p2.1 的候选选择语义也保持不变。

## 阶段指纹

六个可执行阶段分别生成 SHA-256 指纹，统一覆盖：

- 输入内容哈希。
- 当前阶段实际依赖的 Skill 资源版本。
- 依赖版本、硬件型号和工具链版本。
- 模式、容差、benchmark 口径与预算等阶段配置。
- 直接上游阶段的指纹。

指纹不包含绝对源代码工作区路径、时间戳和 `run_manifest.json` 的非语义字段，因此在输出缓存根不变时移动源码工作区，或只更新状态时间，不会造成无效重跑。动态缓存不能迁移到新的输出根：语义校验会拒绝仍指向旧根目录的环境配置或最优检查点。`references/cache/stage-dependencies.json` 明确每个阶段负责的资源，修改最终报告模板不会让前面的编译与精度阶段失效。

## 内容寻址缓存

完成且已验证的阶段产物记录在：

```text
{output_dir}/RunState/cache/{stage}/{fingerprint}/
├── fingerprint.json
├── record.json
└── artifacts/
```

每个快照记录目标相对路径、SHA-256 和字节数。复用前会同时验证指纹、Schema、必需产物、文件大小、内容哈希和关键语义不变量，随后再原子恢复目标文件。`run_manifest.json` 只作为状态索引，不能单独证明缓存有效。

如果精确键对应的缓存损坏，本次计划会重跑该阶段；重跑成功后，旧缓存完整移动到 `RunState/quarantine/{stage}/`，再写入新快照。旧证据可恢复，不会被静默覆盖或删除。

## 断点续跑与失效传播

`plan-resume.py` 按阶段顺序生成 `reuse`、`rerun` 或 `skip` 动作：

- 命中且验证通过：恢复缓存，不重新调度 Agent 或硬件命令。
- 缺失、损坏、指纹变化或显式强制：从该阶段开始重跑。
- 首个失效阶段的所有活动下游阶段一并失效，已验证的上游阶段继续复用。
- `correctness` 仍跳过 `performance-tuning`。
- 崩溃发生在缓存记录完成前时，下次安全重跑，不把半成品视为命中。

恢复已完成的性能调优阶段时，会恢复原有 `best_so_far`、最终代码和已结束的调优状态，不创建新预算，也不会延长旧预算。真实重跑仍使用 p3 固定上限：最多 3 轮、16 次 Worker 调用、1800 秒。

## 按变更范围持续回归

新增变更影响计划，将文件变化映射到最小验证范围：

- 只改最终摘要模板：运行 L1/L2 和 finalization 检查，不重新编译。
- 只改 reduction 策略：保留上游缓存，重跑 reduction 类 L3 及性能下游。
- 只改 Worker 提交或执行后端：重跑环境、Worker 提交与失败恢复检查。
- 修改平台规则：保守选择全部代表算子与 Worker 集成检查。

影响计划只决定“必须验证什么”，不会把未运行的硬件测试声明为通过。

## 保持不变

- `correctness`、`balanced`、`max-performance` 三种模式不变。
- 静态策略路由与实际 benchmark 串行执行不变。
- 固定 3/16/1800 全局预算不变。
- 不加入噪声感知性能选择。
- 最终候选仍从精度通过且比较口径一致的候选中选择最小 `latency_ms`，相同时按 `candidate_id` 稳定排序。
