# Cache and Resume Contract

Read this contract before a full or partial workflow reuses previous outputs. Cache reuse is an optimization, never evidence by itself. Accuracy and performance claims remain governed by the original stage evidence and p3 candidate-selection contract.

## Fingerprint contract

Every executable stage has a desired fingerprint generated by `scripts/state/fingerprint-stage.py`. The fingerprint always covers:

- `input_hash`: content hashes of the declared stage inputs.
- `skill_version`: the content hash of that stage's resources from `references/cache/stage-dependencies.json`.
- `dependency_versions`: the exact runtime/library versions relevant to the stage.
- `hardware_model`: the current measured model, or `null` only for a device-independent stage.
- `toolchain_version`: the current measured toolchain, or `null` only for a device-independent stage.
- `stage_config`: mode, optimization mode, backend, tolerances, benchmark signature, budget policy, and other behavior-changing configuration.
- `upstream_fingerprints`: the fingerprints of direct prerequisite stages.

Absolute source-workspace paths and timestamps are excluded from the digest. Inputs and resources are hashed by logical label plus file content, so moving the source checkout while keeping the output/cache root fixed does not invalidate an entry. Moving the output/cache root invalidates dynamic entries whose verified artifacts embed absolute output paths; rerun those stages instead of restoring stale links.

The per-stage resource registry is the only source for stage-owned Skill dependencies. When an execution-affecting resource is added or moved, update the registry in the same change.

Normalize an in-memory user request into `{output_dir}/RunState/inputs/request.txt` before hashing. Generate a fingerprint with explicit labeled inputs and configuration, for example:

```bash
python {skill_root}/scripts/state/fingerprint-stage.py \
  --stage code-validation \
  --skill-root {skill_root} \
  --input code={output_dir}/KernelGen/triton_code_fix.py \
  --env-config {output_dir}/EnvConfig/config.json \
  --workflow-mode full \
  --optimization-mode {optimization_mode} \
  --upstream code-generation={output_dir}/RunState/fingerprints/code-generation.json \
  --config tolerance='{"rtol": 1e-4, "atol": 1e-5}' \
  --output {output_dir}/RunState/fingerprints/code-validation.json
```

Use these minimum logical inputs:

| Stage | Inputs and configuration included in the fingerprint |
| --- | --- |
| `environment` | Current measured identity, backend choice, Worker/Job configuration, and dependency versions |
| `requirement-extraction` | Normalized request or supplied source; mark device-independent |
| `code-generation` | Extracted requirement, optional original source, environment identity, optimization intent, and upstream fingerprints |
| `code-validation` | Generated code/test, environment identity, tolerances, and code-generation fingerprint |
| `performance-tuning` | Validated code, environment identity, optimization mode, static-plan inputs, benchmark signature, p3 limits, and validation fingerprint |
| `finalization` | Selected or correctness-validated code, selected checkpoint when present, route/mode summary fields, and active upstream fingerprints |

Do not hash `run_manifest.json` wholesale because `updated_at` and resume metadata are non-semantic and would cause self-invalidating fingerprints.

## Cache entry contract

After a stage has completed and its required artifacts have been verified, record it with `scripts/state/stage-cache.py record`. The recorder creates an immutable content-addressed entry under:

```text
{output_dir}/RunState/cache/{stage}/{fingerprint}/
├── record.json
└── artifacts/
    └── {artifact-key}
```

`record.json` stores each artifact's target path relative to `output_dir`, snapshot path, SHA-256, and byte size. Only non-empty files inside `output_dir` may be cached. Failed, running, inferred, or external artifacts are never recorded.

Minimum artifact keys are enforced by the recorder:

| Stage | Required cache keys |
| --- | --- |
| `environment` | `config`, `runtime_info`, `report` |
| `requirement-extraction` | `requirement`; `original_code` is optional |
| `code-generation` | `code`, `report`; cache compatible Step 1–6 files under additional stable keys when present |
| `code-validation` | `code`, `report` |
| `performance-tuning` | `strategy_plan`, `tuning_state`, `best`, `code`, `report` |
| `finalization` | `final_code`, `summary` |

```bash
python {skill_root}/scripts/state/stage-cache.py record \
  --output-dir {output_dir} \
  --fingerprint-file {output_dir}/RunState/fingerprints/<stage>.json \
  --artifact <logical-name>=<absolute-artifact-path> \
  [--artifact <logical-name>=<absolute-artifact-path> ...]
```

A cache hit requires all of the following:

1. Desired and recorded fingerprints are identical.
2. The record validates against `stage-cache-record.schema.json`.
3. Every snapshot exists, is non-empty, and matches its recorded size and SHA-256.
4. Every restored target remains inside the current `output_dir`.
5. No prerequisite stage has been marked for rerun.

Restore with `stage-cache.py restore`. It verifies every snapshot before writing any target, then replaces each target atomically. Never trust a pre-existing target merely because its filename exists.

If an exact-key entry is corrupt, the resume plan marks that stage for rerun. When the completed rerun is recorded, `stage-cache.py` moves the corrupt entry intact under `{output_dir}/RunState/quarantine/{stage}/` before writing the replacement. Quarantine is recoverable evidence; do not silently delete it.

## Resume planning and invalidation

Generate desired fingerprints in dependency order before scheduling expensive work, then run `scripts/state/plan-resume.py`. Stop calculating fingerprints once the first miss or forced rerun is known; downstream fingerprints may be omitted because forward invalidation already requires them to rerun. The active stage order remains:

```text
environment → requirement-extraction → code-generation → code-validation → performance-tuning → finalization
```

`correctness` marks `performance-tuning` skipped. Partial workflow modes use their existing stage subset.

```bash
python {skill_root}/scripts/state/plan-resume.py \
  --output-dir {output_dir} \
  --mode {workflow_mode} \
  --optimization-mode {optimization_mode} \
  --fingerprint <stage>={output_dir}/RunState/fingerprints/<stage>.json \
  [--fingerprint <stage>={output_dir}/RunState/fingerprints/<stage>.json ...] \
  --output {output_dir}/RunState/resume_plan.json

python {skill_root}/scripts/state/apply-resume-plan.py \
  --plan {output_dir}/RunState/resume_plan.json
```

The plan assigns one action per active stage:

- `reuse`: an independently verified cache entry exists and all prerequisites are also reusable.
- `rerun`: the entry is missing, invalid, explicitly forced, or downstream of a rerun.
- `skip`: the stage is disabled by the selected mode.

Invalidation is forward-only. The first changed or invalid stage and every active downstream stage rerun; valid upstream stages remain reusable. A final-summary template change therefore reruns finalization without recompiling. A reduction-strategy change invalidates performance tuning and finalization while preserving environment, extraction, generation, and validation.

Apply a plan with `scripts/state/apply-resume-plan.py`. It restores `reuse` entries, records `cache_status=restored` and the fingerprint in `run_manifest.json`, clears stale state and selected checkpoints for `rerun` stages, and leaves those stages pending for normal execution. A crash before a cache record is complete causes a safe rerun on the next attempt.

## Hardware and budget safety

- Obtain current hardware and dependency identity before calculating fingerprints. Do not reuse a dynamic-stage cache from an unverified previous environment.
- Do not transplant a dynamic cache to a different output root. Semantic verification rejects environment or selected-checkpoint files that still point to the old root.
- Compilation, accuracy, profiling, and performance entries include backend, hardware, toolchain, and comparison configuration. A mismatch invalidates the entry.
- Restoring a completed performance-tuning entry does not restart or extend its old tuning budget. Rerunning performance tuning creates a fresh p3 budget state with the unchanged 3-round, 16-Worker, 1800-second limits.
- Restored candidates retain their original measurements and benchmark signatures. p4 does not alter p2.1/p3 candidate eligibility or add noise-aware scoring.

## Change-impact validation

Use `scripts/validation/plan-change-impact.py` to map changed Skill paths to required validation scope:

- Final-summary template only: L1+L2 finalization checks; no compile/accuracy/performance command.
- Reduction strategy: L1+L2 plus reduction-class L3 and downstream performance checks.
- Worker submission or backend logic: L1+L2 plus environment, Worker submission, and failure-recovery integration checks.
- Platform rules: L1+L2 plus all hardware integration cases.
- Unknown execution-affecting files: conservatively select all L3 cases.

This impact plan chooses what must be validated; it never claims that the selected checks have passed.
