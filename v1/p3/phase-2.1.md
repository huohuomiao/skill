# p2.1 · 归约生成行为兼容修正

p2.1 从 p2 演进，针对用户提供的 softmax 对比报告修正与原版开发行为不一致的问题。完整流程、两次 Code Gen 外层调度、Step 1–6 产物、三层验证体系和最终最优候选选择规则均保持不变。

## 问题定位

阶段 2 合并 Code Gen 角色时，文件契约被保留，但原版两个影响性能搜索路径的生成约束被压缩掉：

1. 完整优化流程中的归约基线应保留 Kernel 内部分块循环；p2 的合并角色允许直接生成全轴向量化实现，使 `reduce-opt` 没有循环与跨遍加载可优化。
2. p2 的精简 autotune 文档没有明确区分“静态候选生成”和“真实编译淘汰”，可能因保守 NRAM 估算提前移除小并行块和流水候选。

用户报告中的 `(4096, 4096)` float32 softmax 因此出现 `0.1450 ms` 与原版 `0.1140 ms` 的差异。该数据用于定位回归，不作为 p2.1 已复现性能的声明。

## 修正内容

- 新增 `optimization_intent`：
  - 完整流程传入 `handoff-to-tuning`，归约 Code Gen 保留后续策略可处理的分块循环。
  - 独立 Code Generation 使用 `standalone`，仍允许直接生成资源安全的向量化实现，不为触发优化而故意增加冗余工作。
  - Existing-code 快速路径始终保留用户源码结构。
- 新增归约基线契约：softmax 类采用 `max → sum → normalize-store` 三遍分块结构，并在 Step 4 写入 `optimization_surface`。
- 新增确定性校验脚本：完整优化流程若把归约提前折叠成全轴向量化、遗漏分块循环或遗漏必要候选，会在 Kernel Builder 前失败并只回退到 Designer。
- 修正 autotune 规则：NRAM 使用生命周期模型；仅在确定越界时静态淘汰，估算不确定但合理的候选交给真实编译判断。
- softmax 行归约在语义有效时保留 `BLOCK_M=4`，并为支持流水的后端保留 `num_stages=[1,3]`。它们只是候选，最终配置仍由真实精度和性能测量决定。

## 新增验证

- L1 检查 p2.1 归约契约、Schema、校验脚本和调用链是否完整。
- L2 新增两个行为场景：完整调优保留优化面；独立生成不制造优化空间。
- 新增 3 个契约回归测试：
  - 接受包含三遍循环、`BLOCK_M=4` 和 `num_stages=[1,3]` 的 softmax handoff。
  - 拒绝伪装成 handoff 的直接全轴向量化规格。
  - 允许 standalone 选择直接向量化形式。

## 验证边界

当前仅完成静态与离线行为修正。只有使用同一 softmax、硬件、工具链和 `do_bench` 口径完成真实 L3 回归后，才能判断 p2.1 是否从 `0.1450 ms` 恢复到接近 `0.1140 ms`。

本地门禁结果：L1 通过（2.637 秒），L2 通过（1.047 秒），L1+L2 总入口通过（3.829 秒），Skill 快速校验通过。
