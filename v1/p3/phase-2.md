# p2 · 阶段 2：降低上下文与代理调度开销

p2 从 p1 的三层验证基线演进而来。算子开发流程、Step 1–6 兼容产物、精度门禁和最终最优产物选择规则保持不变；本阶段只收敛规则来源、代理边界和阶段交接信息。

## 优化前的判断

- 原 Code Gen 将设计链拆成 4 个角色、生成链拆成 2 个角色，正常路径需要 6 次外层调度；相邻角色反复读取相同需求和平台规则。
- 执行后端规则与平台约束散落在工作流、角色和策略中，修改一条规则容易产生多个不一致副本。
- 下游依赖完整报告判断状态，交接时会重复装载大量历史上下文。
- 大策略文档混合了匹配条件、执行步骤和长示例，即使场景不命中也可能被整体读取。

因此 p2 采用“唯一事实源 + 合并相邻角色 + 精简状态摘要 + 示例按需加载”的方案，不提前实现阶段 3 的优化预算、停止阈值或模式策略。

## 已实现内容

1. 两个唯一事实源：
   - `references/contracts/execution-backend.md` 只管理 local/worker 选择、Worker 调用、超时和退出码。
   - `references/backend/platform-rules.md` 只管理设备、Grid、NRAM、dtype、Libdevice 和平台优化约束。
2. Code Gen 合并为两个外层角色：
   - Kernel Designer 一次生成 Step 1–4 JSON。
   - Kernel Builder 一次生成 Step 5 kernel 与 Step 6 test。
   - 原 Step 1–6 文件名和下游契约不变，已有调试与兼容链路可继续使用。
3. 新增根级 `run_manifest.json`：记录工作流模式、阶段状态、产物路径、执行后端和已选检查点；阶段通过脚本原子更新，下游不再为判断状态重读全部报告。
4. 精简高频策略文档：正文只保留准入条件、转换步骤和不变量，长示例仅在匹配场景时从 `references/examples/` 加载。
5. 将阶段 2 架构约束加入 L1/L2：自动检查事实源唯一性、旧角色入口移除、正常路径两次调度、manifest Schema 与状态转换。

## 离线测量

| 指标 | p1 | p2 | 变化 |
| --- | ---: | ---: | ---: |
| 正常 Code Gen 外层调度 | 6 次 | 2 次 | 降低 66.7% |
| 正常 Code Gen 核心文档体积 | 95,816 B | 13,899 B | 降低 85.5% |
| 正常 Code Gen 核心文档行数 | 2,332 | 337 | 降低 85.5% |
| L2 固定行为场景 | 21 | 23 | 新增正常/快速路径调度检查 |

文档体积是上下文开销的离线代理指标，不等同于真实 Token 计费。真实 Token、精度和硬件性能变化需要在后续代表算子回归中记录；p2 不生成没有硬件证据的性能结论。

## 验证结果

- L1：通过，本地运行约 5 秒，满足 30 秒门禁。
- L2：通过，本地运行约 1 秒；包含 23 个固定场景、5 个 P0 回归测试和 3 个 p2 状态契约测试。
- L3：本次未运行，因为没有提供真实硬件集成套件；不据此声明精度或性能提升。
