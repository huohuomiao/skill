# 版本与阶段对应关系

## 1. 当前采用的阶段定义

本项目中“文件夹版本号”和“阶段号”曾经两次调整，不能只看 `vN` 推断阶段。以当前需求
为准，阶段顺序是：

1. 阶段 1：P0 契约修复与验证基线；
2. 阶段 2：降低 Token 和代理调度开销；
3. 阶段 3：按需优化和全局预算；
4. 阶段 4：缓存、断点续跑和持续回归。

## 2. 总表

| 文件夹 | 当前阶段定位 | 基于 | 主要内容 | 明确不包含 |
|---|---|---|---|---|
| `v1` | 阶段 0 / 原始基线 | 原始代码 | 四个 Skill、串行多代理生成和原优化链 | 后续所有修复与控制面 |
| `v2` | 阶段 1 | `v1` | P0 契约修复、删除废弃 `analyzer_rep.py`、L1/L2/L3 验证 | 代理合并、按需预算、跨运行缓存 |
| `v1_1` | 阶段 2 独立对照版 | `v1` | Code Gen 6→2、Review 2→1、路径式上下文、调度度量 | `v2` 的 P0 累计修复、阶段 3/4 |
| `v3` | 阶段 3 的早期实现（历史文档称阶段 2） | `v2` | correctness/balanced/max-performance、静态策略路由、全局预算 | Code Gen 代理合并、跨运行缓存 |
| `v3_1` | 阶段 3 正式版 | `v3` | 按需优化、全局预算、安全 `plan --resume`，恢复不清零预算 | 阶段 2 代理合并、阶段 4 跨运行缓存 |
| `v4` | 阶段 4 | `v3` | 内容寻址缓存、阶段 DAG、断点续跑、预算续跑、持续回归 | 本次 `v1_1` 的代理合并未自动合入 |

## 3. 为什么 `v3` 的说明书写“阶段 2”

`v3/STAGE2_OPTIMIZATION_MANUAL.md` 是旧路线下生成的文件，当时“按需优化与全局预算”被称为
阶段 2。随后需求把“降低 Token 和代理调度开销”正式插入为新的阶段 2，并要求“按需优化
和全局预算”放入 `v3_1` 作为阶段 3。

所以：

- 按文件历史：`v3` 文档标题仍是“阶段 2”；
- 按当前功能路线：`v3` 是阶段 3 的早期实现，`v3_1` 是阶段 3 的正式版本；
- 不建议为了统一标题直接改旧文件，否则会破坏版本审计。用本映射表解释即可。

## 4. 各阶段交付内容

### 阶段 0：v1

用于保留原始行为和做 before/after 对照。Code Gen 普通路径有六个串行代理，Review 失败链有
两个代理；缺少统一离线契约门禁。

### 阶段 1：v2

重点是“先正确”：修复 P0 调用/产物契约，删除废弃分析脚本，补充标准库验证、行为 fixture
和真实 MLU 验证说明。它没有做上下文去重和代理合并。

### 阶段 2：v1_1

重点是“少调度、少重复上下文”：普通路径 8→4 或 10→5，保留原 Step 产物，增加可执行
调度/静态上下文度量。它是为了清晰对比直接从 v1 分出，因此不是 v2 的后继累计版。

### 阶段 3：v3 与 v3_1

`v3` 首先实现按模式路由和 Optimizer 全局硬预算；`v3_1` 把这一能力正式归入当前阶段 3，
并增加安全恢复：已有状态必须使用 `plan --resume`，输入、模式或预算不兼容时拒绝恢复，不能
通过删状态绕过已消耗预算。

阶段 3 的预算范围是 Optimizer，不覆盖 EnvConfig、Extractor、Code Gen 和 Code Review。

### 阶段 4：v4

在 v3 控制面之上加入：外层阶段 DAG、内容寻址缓存、上游变更向下游失效传播、Code Gen
内部检查点、Optimizer 状态续跑、回归 JSON 契约和 CI/Nightly/Release 分层。

`v4` 从 `v3` 演进并自行带有安全预算恢复，但不是从本次 `v1_1` 分支生成，所以不能假设
它已拥有 Design/Build/ReviewAndFix 三个合并角色。

## 5. 分支关系

```text
v1（原始基线）
├─ v2（阶段 1：P0 + 验证）
│  └─ v3（当前阶段 3 早期版：按需 + 预算）
│     ├─ v3_1（阶段 3 正式版：安全预算恢复）
│     └─ v4（阶段 4：缓存 + 续跑 + 回归）
└─ v1_1（阶段 2 独立版：Token + 调度）
```

这不是一条完全线性的累计发布链。`v1_1` 是为隔离测量阶段 2 收益而建立的旁支。

## 6. 如何选择

| 目的 | 建议版本 |
|---|---|
| 复现最初行为 | `v1` |
| 验证 P0 修复 | `v2` |
| 单独评估代理数与上下文降幅 | `v1_1` |
| 使用按需优化和预算安全恢复 | `v3_1` |
| 使用缓存、断点续跑和持续回归 | `v4` |

如果目标是生产使用“阶段 1 + 2 + 3 + 4”的全部能力，需要做一次明确的集成版本：以 `v4`
为基线移植 `v1_1` 的 Code Gen/Review 合并和调度度量，随后同时运行 `v1_1` 与 `v4` 的离线
套件和真实 MLU 回归。当前任一单独文件夹都不应被描述为已经包含四个阶段的全部改动。

## 7. 推荐阅读顺序

1. `v2/STRUCTURE_COMPARISON.md`：阶段 1 的 P0 修复；
2. `v1_1/STAGE2_TOKEN_AND_DISPATCH_MANUAL.md`：阶段 2；
3. `v3_1/STAGE3_OPTIMIZATION_MANUAL.md`：阶段 3；
4. `v4/STAGE4_CACHE_RESUME_REGRESSION_MANUAL.md`：阶段 4；
5. 每版 `HOW_TO_VALIDATE.md`：对应版本的验收方法。
